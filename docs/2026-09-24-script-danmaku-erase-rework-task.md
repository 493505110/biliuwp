## 一、任务目标

让宿主在「元件被隐藏（`visible=false`）/ 不透明度归零（`alpha=0`）/ 被摘除 / 条目离场」这四条路径上，把它先前画在主画布上的像素**干净擦掉**，同时**不伤及同帧其它元素**——既不留残影，也不打出空洞。

判据是两支：
1. **不脏**：尾部（124s 之后）不得出现大面积实心块；
2. **不少画**：中段（105~122s）亮像素不低于本任务书第四节的基线值。

现状是「两版各对一头、合不起来」：已推送的 `2ee4357` 尾部干净、中段偏暗；未收敛的精确擦除版中段正常、尾部失效。

## 二、必须先建立的机制理解

### 2.1 渲染模型

宿主是**保留模式**渲染器：元件树 + 每个元件一份复合层（composite canvas，`rebuildComposite` 内先 `clearRect` 再画子元素）。每帧只做两件事：

1. `prepareElement(element)`：自底向上刷新复合层，返回「内容是否变了」，变了就在该顶层元件上置 `dirtyCandidate`；
2. `paintDirtyElements()`：先 `flushEraseRects(pendingEraseRects)` 把上一帧攒下的擦除矩形在主画布上清掉，再**补画被擦到的邻居**，最后合成脏元素。

关键约束（读代码时以现场为准）：

- `lastPaintedRect` = 元件在主画布上的矩形（**设备像素**，含 `DIRTY_RECT_PADDING`）；
- `pendingEraseRects` 由属性 setter 侧入队，**只能在帧首 flush**；
- `paintDirtyElements` 在宿主里**有两个同名实现**，后一个才会被调用（契约测试为此加了 `PaintBody()`）——读代码别读错那个；
- 合成顺序：先邻居、后脏元素，目的是不把层叠顺序反过来。

### 2.2 四条擦除路径的现状

| 路径 | 入口 | 处理 |
| --- | --- | --- |
| 摘除 | `removeChildFromParent` / `detachElement` | 摘链**前**处理旧像素（摘了就找不到祖先），已修 |
| 隐藏 | `markElementHidden`（`visible=false`） | 已修，走「最近一个有主画布矩形的祖先」的整块矩形 |
| 淡出 | `markElementHidden`（`alpha=0`） | 已修，同上（**粗粒度，是当前中段偏暗的嫌疑点**） |
| 条目离场 | `hadActiveItem` + `clearSurface()` | 最后一个条目离开窗口的整幅清空，已修 |

### 2.3 作品侧的图层模型（Akari）

- `Akari.Display.Layer.update(time)` 只写 `source.visible = false/true`，**从不删元素**；所有显示对象用 `lifeTime: 810114514` 哨兵创建；
- 组合：Comp0 = 前 3750 tick（中段动画），Comp1 = `startTime:3750, duration:27750`（尾部：字幕层 + 25 个 replicate 图层 + `lineStyle(1,0x1A1A1A)` 细线网格 + 半透明白六边形光斑）；
- **122.5s 之后是换场景，不是弹幕层结束**，条目时间窗应为组合长度 **333s**（早期文档里「122.5s 整层消失」的前提已作废，见 `6ced6ef`）。

## 四、待解决缺陷与本轮实测数据

### 4.1 量法

真 Chromium（WebView2 同源引擎）+ 探针页，窗口 333s、11 条真实 mode=8 脚本，覆盖播放头 87.75→142.9s，1280×720。判据为**画布亮像素占比**：取帧后转灰阶，灰度 > 60 的像素占比。

**重要前提：这作品自身带随机源**（主脚本 `entry_10_1147217315.js` 里有 **61 处 `Math.random()`**，例如 Comp1 的六边形光斑 `beginFill(0xffffff, Math.random() * 0.3)`）。同一版本不同次运行，尾部亮像素占比实测出现过 **0.0287 与 0.1356** 的差异。**因此单次抓帧比数值不足以定论**，见第六节验收口径。

### 4.3 已试过但不成立的两个方向（补丁已入库，见 `docs/patches/`）

两份补丁都**能对 `2ee4357` 干净应用**（`git apply --check` 通过），因此可直接复现，不必重新摸索。
它们是「候选」不是「结论」：**两条路都没收敛**，上手时请把它们当反例读，别再原样重推。

**候选补丁 A：精确擦除** —— `docs/patches/2026-09-24-script-danmaku-erase-wip-precise-erase.patch`
（改 `script-danmaku-host.html` + `tests/host/retained-mode.test.js`；这是唯一权威副本，原先的本地 stash 已删除）：
- 做法：新增「把元件本地包围盒沿祖先链逐级套变换」的落点计算，隐藏/淡出时只擦元件自身落点，而非最近祖先的整块矩形；配套用例 D29（隐藏小元件不得擦到同组远处的兄弟）。
- 实测：中段回来了（118s 0.4320 / 120s 0.4544 / 122s 0.7163，与 v6 同级），**尾部又脏**（124s 之后 0.35~0.50）。
- 未定论：形状类元件上坐标是对的（D29 反向验证通过），容器/图层分支的落点还没与宿主既有 `compositeChildBounds` 对齐。

**候选补丁 B：粗粒度 + 补画缺口** —— `docs/patches/2026-09-24-script-danmaku-erase-wip-repaint-gaps.patch`
（只改 `script-danmaku-host.html`；这是唯一权威副本，原先的本地 stash 已删除）：
- 做法：在 `paintDirtyElements` 里补三处——① 邻居包围盒未知（`lastPaintedRect` 为 null）也补画；② 候选元素「矩形没变就跳过」的短路，改为「被擦除矩形命中则不跳过」；③ alpha 归零的邻居不参与补画。
- 实测：①+② 让中段改善（119s 0.5823、**121s 1.0000 与原录屏一致**），但尾部出现实心块（128s/136s 经看图确认有灰蓝块与黑块，亮像素 0.099~0.135）；再加 ③ 后尾部反而恶化到 **0.547~0.888**（大面积实心）。

### 4.4 当前怀疑（未证实，供上手参考）

- 粗粒度擦除（擦「最近祖先的整块矩形」）本身没错，**错在擦完之后没有把落在该矩形内的所有元素重新合成**；`2ee4357` 的中段偏暗与 4.3 的第二版一致指向这条。
- 候选元素的重绘短路（「位置与上帧一致就不必再合成」）是主要漏点嫌疑：被擦掉的像素不会因为矩形没变而回来。
- 精确擦除方向要成立，必须先让容器/图层分支的落点与宿主既有包围盒算法（`compositeChildBounds` / `boundsAdd` / `boundsReset` / `boundsResult`）对齐。

## 五、已知陷阱（别踩）

1. **移动路径绝不能擦祖先矩形**。把「向上擦祖先」挂进 `markElementMoved` 会在每帧热路径上打洞：曾导致中段 115s 与原录屏相关从 +0.871 掉到 **-0.382**。移动只允许 `parent.compositeDirty = true`。
2. **`alpha=0` 与 `visible=false` 是同一族**（Akari 用 `Layer.update` 写 visible 实现退场，作品里还有整幅 1280×720 的关键帧 alpha 淡出），但**恢复可见时必须让祖先复合层重烘**，否则那块永久空洞。
3. 擦除后要么保证被擦区域内的元素全部重画，要么别擦那么大——**别只做一半**（本任务书的现状就是各做一半）。
4. **宿主里有两个同名 `paintDirtyElements`**；另注意重构时不要引入与既有函数同名的实现（曾用 `elementLocalBounds` 覆盖了宿主原函数，套件从 29/29 掉到 11/29）。
5. **宿主改动后必须重建探针页**（把当前宿主内联进探针 HTML），否则是拿旧代码验证新修复。
6. **判断画面必须读 `canvas.getImageData()`**：页面切到后台 rAF 会停摆，CDP 截图会返回旧帧；抓帧前把页面底色置黑，避免透明画布被压白底。
7. **不要单次抓帧下结论**（见 4.1 的随机源）。
8. 不提交 `/tmp` 下的临时文件；不动仓库根目录三个未跟踪清单 md（`biliuwp-engineering-checklist.md`、`biliuwp-security-checklist.md`、`biliuwp_代码质量与可维护性优化建议清单.md`）；**不动 BAS 弹幕控件与互动弹幕控件**，只改脚本弹幕相关代码。

1. **探针页**：把当前宿主内联进一个自包含 HTML（含 11 条真实 mode=8 脚本夹具），`python3 -m http.server 8899 --bind 127.0.0.1` 起服务，浏览器打开该页。
2. **夹具**：`tests/host/fixtures/real/entry_08_1147140491.js`（Akari 库，50,050 字符）、`entry_10_1147217315.js`（主脚本，353,975 字节），另有 9 条 progress 0 的小条目。
3. **参考录屏**：BV1c7411H7jF（cid=148436020，2020-02-05 留档，143.1s）；原作品 av2669196。作品视频轨纯黑静止（20s/88s/135s 三帧 md5 同为 `2d4387e1b1`），弹幕层才是画面内容。
4. **官方弹幕包**（复核用）：`api.bilibili.com/x/v2/dm/web/view?type=1&oid=4369799&pid=2669196` → `i0.hdslb.com/bfs/dm/6cadf9a33a4db9c861b5cdd31e3224852bfcc51d.bin`（796,313 字节，md5 前 12 位 `713a07013f6b`），解出正好 11 条 `mode=8`，与夹具一一对应。
5. **量亮像素**：录屏/渲染各按时长抽帧，`ffmpeg -ss <t> -frames:v 1 -f rawvideo -pix_fmt gray`，统计灰度 > 60 的占比；同一内容秒要减去起始偏移（本套为 87.75s）。
6. **NCC**：两条片逐帧算平均亮度时间线，在 ±N 秒范围内做归一化互相关找峰值（当前工具链实测峰值 ±0.25s / +0.899）。
7. **看图**：抽关键秒左右并排拼图（左=我方，右=原录屏），只回答「有无大面积实心块、形态是否一致」，不要依赖文字标签判断。
